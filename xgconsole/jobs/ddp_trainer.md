motivation: Owner: multi-GPU training would be faster. The dataflow trace showed the step is compute-bound and unbatched (one shape per step), so data-parallel across the 4 L40S of one node is the natural speedup; must preserve single-GPU behavior exactly.

- 2026-08-23 12:55 [master] Job started.
- 2026-08-23 13:15 [ddp-engineer] Multi-GPU training support is written: the trainer can now split an epoch's shapes across several GPUs on one node and average the gradients, with the single-GPU path left exactly as it was. Two test jobs are queued on the cluster, one to check that two GPUs learn the same thing one GPU does, one to measure how much faster four GPUs actually are.
- 2026-08-23 13:39 [ddp-engineer] Checked that multi-GPU training gives the same answer as one GPU. Over the same 200 shapes the two runs track each other to within a fraction of a percent every epoch, a two-GPU run saved a checkpoint the evaluation script loads and scores normally, and the periodic validation still runs. Measuring the speedup now.
- 2026-08-23 14:28 [ddp-engineer] Measured the speedup on a four-GPU node: four GPUs get through 2.3 times as many shapes per second as one, and 2.9 times with a small batching change. The shortfall from a clean four times is not the GPUs talking to each other, it is that shapes differ hugely in size and every GPU has to wait for whichever one drew the biggest shape. The code is committed, pushed and deployed to the cluster.
- 2026-08-23 15:28 [ddp-engineer] Also checked that the change leaves ordinary one-GPU runs alone, which matters because a long training run was starting against it. The check needed a control: this model does not reproduce itself exactly even when run twice with the same settings, and the difference across the change is no bigger than that. Cleaned up 64 GB of throwaway test checkpoints.
- 2026-08-23 15:28 [ddp-engineer] The trainer can now use several GPUs at once. Four GPUs get through 2.3 times as many shapes per second as one, or 2.9 times with a small batching change, and the training itself is unchanged: runs at one, two and four GPUs produce the same loss curve on the same data. Existing single-GPU jobs are unaffected and need no edits. A template and a written recipe for moving a run onto four GPUs are in the repo.
- 2026-08-23 15:37 [ddp-engineer] Proved the change is safe for ordinary one-GPU runs, which was the open question: the very first training step comes out to the exact same number, bit for bit, before and after the change. Later steps drift a little, but the old code drifts from itself by just as much when run twice, so that is the hardware and not the change.
- 2026-08-23 15:46 [ddp-engineer] One correction to an earlier note: I had passed on a report that a gap I found in one dataset folder was a false alarm from the shared filesystem. Rechecked it from a second machine and by listing the folder directly, and the gap is real: 41 of 286 shapes there never got their conditioning file built. It is a folder nothing trains on, so nothing is affected, but the number stands.
- 2026-08-23 15:58 [ddp-engineer] Follow-up, approved by the team lead: the training code no longer trusts the shared filesystem when it says a file is missing. It now checks the folder listing, which tells a genuine gap apart from a passing glitch. A glitch is retried once and reported; a real gap fails exactly as it did before. This is what cost a multi-day job its slot yesterday. Shipped with tests covering both cases, checked against a folder with a real gap and one without.

The check now lives in one shared place instead of two copies. Tests grew from 19 to 44.
